Repository-Level API Security

August 4, 2026

In a backend I built for a webapp, the database has model/service/repo layers. The repository layer was meant to have some built-in security.

There's a BaseRepository with basic CRUD functions, and then a UserOwnedRepository which overwrites those functions and requires a user_id as a parameter. The idea being that the API layer would require an auth token, extract the user id from it, and the repo/service layers would be restricted from editing anything not owned by the user who made the request.

The Problem

The UserOwnedRepository only overrides the getter functions. This convention would hold until I forgot about it while building a new repo function and thought "wow this would be simpler if I just passed in the entity's ID"

So it needs to be rebuilt. Unfortunately, this is going to change the function signature for most repo functions, which is going to require refactoring the service methods that call them, and in fact the API layer needs to be refactored as well.

Catchlist Architecture Review

July 27, 2026

Catchlist is a productivity application for managing tasks, projects, routines, and commitments — but it's primarily an exercise in building a small app with commercial-grade infrastructure: a frontend/backend split, dev/staging/production environments, CI/CD, automated testing, and an architecture where every behavior has an obvious home.

The writeup walks through the full system structure, driven by a single guiding principle: entities flow through a consistent pattern of model, repository, service, presenter, API routes, and webapp routes, keeping responsibilities clear at every layer.

Tradeoffs

Splitting API and webapp into two services adds deployment complexity, but enforces a clean separation between presentation and backend logic. Timezone and recurring event handling go beyond the usual "store in UTC" advice to preserve intent across DST changes. And explicitness is deliberately favored over minimalism — even when it means more files — because complex is better than complicated.

Lessons Learned

The review covers modeling recurring events without losing their meaning, the pain of an inverted testing pyramid (a glut of brittle end-to-end tests), and how repository layers can silently drift into containing business logic.
